# 4Dセッション：デスクトップからWebまでを1つの共有セッションで

著者：Al Mahdi Bakkali（4D Inc. テクニカルサポートエンジニア）

テクニカルノート 26-06

## 概要

4D Secure OTPデモアプリケーションは、クロスプラットフォームで動作する本人確認・書類確認システムです。セッション管理のための冗長な仕組みをなくすことを目的に設計されており、クライアント側のSessionオブジェクトを活用することで、サーバー側に処理を委ねることなく、4Dリモートのデスクトップクライアントから直接セッションのメタデータを参照し、ワンタイムパスワードを生成します。

セッションの状態は、4Dのデスクトップフォーム、Webコンソール、モバイルデバイスという3つのアクセスポイントの間で同時に同期されます。このシステムは、4D 21で導入され4D 21 R3で拡張された、相互に関連する4つのセッション機能を実装しています。リモートクライアントからの**Session.info**プロパティへの直接アクセス、デスクトップセッションでの**Session.createOTP()**の呼び出し、異なるクライアントを1つのセッションコンテキストに結び付けるクロスプラットフォームのセッション共有の仕組み、そしてすべての参加者に状態の変化をリアルタイムで伝える共有オブジェクト**Session.storage**です。

## はじめに

最近の4Dアプリケーションにおいて、セッション管理はデータアクセス、ユーザー体験、アーキテクチャが交わる位置にあります。セッションとは、ユーザーが何をできるか、どのデータを参照できるか、そしてアプリケーションの各部分がどのように通信できるかを決める実行時のコンテキストです。デスクトップのユーザー、Webインターフェース、モバイルデバイスが同じタスクで協調する必要があるマルチチャネルのアプリケーションでは、セッション管理はこの連携を可能にする重要な基盤となります。

4D 21 R3より前にも、リモートユーザーセッション（remote user session）は存在し、サーバー上でアクセスすることができました。しかし、4Dリモートクライアントから直接実行した場合、Sessionコマンドは`Null`を返していました。そのため、セッション情報を利用できるのは、HTTPハンドラー、RESTハンドラー、ストアドプロシージャー、あるいは明示的にサーバーへ送られたメソッドなど、サーバー側の実行コンテキストに限られていました。その結果、フォームメソッドやオブジェクトメソッドなどクライアント側のコードでセッションデータが必要な場合、開発者はセッション情報をクライアントに返すためだけの専用のサーバー側メソッドを作成しなければならないことが多く、不要な複雑さが加わっていました。

4D 21 R3でSessionコマンドがリモートクライアントに対応したことで、この複雑さは大幅に軽減されます。フォームメソッドからクライアント側のコードで直接**Session.info**を呼び出したり、**Session.userName**などのプロパティにアクセスしたりできるようになりました。また、**Session.createOTP()**などの関数を呼び出して、Webブラウザーが同じユーザーセッションに参加するためのワンタイムパスワード（OTP）を生成することもできます。ワンタイムパスワードの仕組みによるセッション共有機能と組み合わせることで、これまでは追加の基盤やサーバー側の独自メソッドを必要としていた高度なマルチチャネルのワークフローが可能になります。

本書では、実践的なデモアプリケーション「4D Secure OTP」を使って、これらの機能を実際の文脈の中で説明します。4D Secure OTPは、本人確認（KYC：Know Your Customer）ワークフローのための本人確認コンソールです。コンプライアンス担当者がデスクトップで確認セッションを開き、対象者がモバイルデバイスでQRコードによるチャレンジに答えて本人であることを証明し、本人確認書類をアップロードします。担当者は提出内容を確認して判定を下します。これらすべてが、1つの共有された4Dセッションの中で行われます。このシナリオでは、リモートクライアントのコードから直接利用できるようになったセッション管理機能の多くを使用します。

## 動作環境

本テクニカルノートに付属するデモ用の4Dアプリケーションは、WindowsとmacOSの両方に対応しており、以下の最小環境が必要です。

- **4D 21 R3** - 4Dリモートクライアントから**Session**コマンドとSession.infoプロパティを利用するために必要
- **4D 21以降** - デスクトップセッションでの**Session.createOTP()**、および**setPrivileges() / clearPrivileges()**のブール型の戻り値に必要
- **Webサーバーを有効にした4D Serverライセンス**— HTTPルートの提供とユーザーポータルのホストに必要
- **4D Remoteライセンス**— ユーザーのデスクトップセッションに必要。このセッションがOTPを発行します
- **Windows 11またはmacOS Tahoe**

> **注**：デスクトップセッションには3つの構成があります。クライアント/サーバーアプリケーションのリモートユーザーセッション（Sessionオブジェクトはサーバー側とクライアント側の両方からアクセスできます）、ストアドプロシージャーセッション（すべてのストアドプロシージャーで共有される仮想のサーバーセッション）、そしてシングルユーザー版4Dのスタンドアロンセッション（standalone session）です。**スタンドアロンセッションは開発時に特に便利で、このアプリケーションにも使用できます。**最終的なアプリケーションがシングルユーザーとクライアント/サーバーのどちらで運用されるかに関わらず、サーバーを用意しなくても、OTPの生成やWebアクセスとの共有を含むすべてのセッション関数を利用できます。

## なぜクライアント側のセッションなのか

4D 21 R3より前は、セッション情報にアクセスする必要があるクライアント側のコードは、サーバー側の実行を通じてその情報を取得しなければなりませんでした。クライアント側のコードは**Session**オブジェクトに直接アクセスできなかったため、セッション情報を取得するにはサーバー側の仲介メソッドに頼る必要がありました。

4D 21 R3では、4DリモートクライアントからSessionを呼び出すと、カレントのリモートユーザーセッションオブジェクトが直接返されます。セッション情報を読み取るだけのために、サーバー側へ追加のリクエストを送る必要はありません。

Sessionコマンドにより、クライアント側のコードから以下の機能を直接利用できるようになりました。

- **Session.info** - ユーザー名、マシン名、IPアドレス、セッション識別子、セッションの種類、作成日時などのセッションのメタデータ
- **Session.id** - よく使われるセッションプロパティへの直接アクセス
- **Session.storage** - セッションで共有される、セッション単位のストレージ
- **Session.createOTP()** - Webクライアントが同じセッションに参加するためのワンタイムパスワードの生成
- **Session.hasPrivilege() / Session.getPrivileges() / Session.isGuest()** - クライアント側とサーバー側の両方で利用できる、アクセス権（privilege）を確認する関数

ただし、以下の操作は引き続きサーバー側でのみ実行できます。

- **Session.setPrivileges()**
- **Session.clearPrivileges()**

アクセス権の変更はサーバーの役割であるため、これらの関数を4Dリモートクライアントから直接呼び出すとエラーが発生します。これらの機能を組み合わせることで、独自の基盤を用意しなくても、デスクトップクライアントと1つ以上のWebクライアントが1つの共有セッションコンテキストの中で連携するマルチチャネルのアプリケーションを構築できます。

## クライアント側でセッションのメタデータを読み取る

### Session.infoオブジェクト

Session.infoプロパティは、カレントセッションの識別情報とコンテキスト情報を格納したオブジェクトを返します。4Dリモートクライアントのコンテキストでは、ユーザーを識別するメタデータ、つまりユーザーID、接続コンテキスト、セッションの作成日時、そして次の節で説明するその他のプロパティを提供します。

デモアプリケーションでは、デスクトップフォームのSession_FormがOn LoadイベントでSession.infoを使用し、ユーザーの識別情報パネルに値を表示します。これはユーザーが最初に目にするフォームであり、サーバーにメソッドを送ることなく、クライアントのコンテキストでセッションのメタデータをすぐに利用できることを示しています。

![](fig-01)

以下は、Session_Formのフォームメソッドからの抜粋です。すべての値はSession.infoから直接取得しており、サーバー側での実行は一切ありません。

```4d
Case of
    : (Form event code=On Load)
        var $info : Object:=Session.info

        OBJECT SET TITLE(*; "valType";    String($info.type))
        OBJECT SET TITLE(*; "valUser";    String($info.userName))
        OBJECT SET TITLE(*; "valMachine"; String($info.machineName))
        OBJECT SET TITLE(*; "valIP";      String($info.IPAddress))
        // continue populating form objects
End case
```

### プロパティ一覧

リモート（デスクトップ）セッションでSession.infoから取得できるプロパティの例を以下に示します。すべてのプロパティは読み取り専用です。

| プロパティ | 型 | 説明 |
|---|---|:---|
| `type` | Text | セッションの種類。4Dリモートクライアントの接続では`"remote"`を返します。 |
| `userName` | Text | アプリケーションへのログイン時に入力された、ユーザーディレクトリの4Dユーザー名。 |
| `machineName` | Text | クライアントマシンのネットワーク上のホスト名。 |
| `IPAddress` | Text | クライアント接続のIPアドレスとポート。形式は`address:port`です。 |
| `ID` | Text | 一意のセッション識別子（UUID形式）。セッションが存続する間は変わりません。 |
| `creationDateTime` | Text | セッションが確立された日時のISO 8601形式のタイムスタンプ（例：`2026-06-24T09:31:00.000Z`）。 |

> **利用できるコンテキスト**：Session.infoは、リモートクライアントのコンテキスト（4D 21 R3）とサーバー側の実行コンテキストの両方で利用できます。返されるプロパティはセッションの種類によって異なります。WebセッションではuserNameは返されますがmachineNameは返されません。一方、リモートセッションでは上記のすべてのプロパティに加え、さらに多くのプロパティが返されます。

セッションの種類ごとのプロパティの全一覧については、4Dのドキュメントを参照してください。

## デスクトップセッションでのSession.createOTP()

Session.createOTP()は、もともとWebセッション用に導入された関数で、生成したトークンをURLに埋め込むことで、WebクライアントがほかのWebクライアントとセッションを共有できるようにするものでした。4D 21では、この関数がリモートユーザーセッション（デスクトップセッション）でも使えるように拡張され、既存のデスクトップセッションにWebブラウザーを招き入れることができるようになりました。

この関数は、有効期間が短く一度しか使えないトークンを生成します。このトークンを$4DSIDクエリパラメーターとしてURLに付加すると、4Dサーバーは新しいHTTP接続を、トークンを作成したセッションに関連付けます。

![](fig-02)

対象のメソッドからの抜粋を以下に示します。

```4d
var $token : Text:=Session.createOTP(10)
```

トークンはシステムで設定されたOTPのタイムアウト時間を過ぎると失効し、それ以降にURLにアクセスすると、セッションの有効期限が切れたことを示すメッセージが返されます。

デモアプリケーションでは、getOTPプロジェクトメソッドがトークンを作成し、有効なOTPを使った場合にのみ共有される共有セッションストレージを初期化します。コードの抜粋を以下に示します。

```4d
Use (Session.storage)
    Session.storage.desktopMessage:=New shared object("openedAt"; Timestamp)
End use
```

Session_Formのボタンのオブジェクトメソッドは、このトークンを受け取って完全なURLを組み立て、システムのブラウザーで開きます。組み立てられたURLは、OTPを$4DSIDクエリパラメーターとして含んでいます。これは、セッションに紐付いたURLを作成するための4Dの標準的な仕組みです。コードの抜粋を以下に示します。

```4d
var $otp : Text:=getOTP
var $port : Integer:=$serverInfo.options.webPortID
var $host : Text:=$serverInfo.options.webIPAddressToListen[0]
var $url : Text

$url:="http://"+$host+"/init?$4DSID="+$otp

OPEN URL($url)
```

URLに付加されたトークンは生成されたOTPと一致するため、ブラウザーにセッションの共有が許可されます。このコードにより、ブラウザーで次のような構造のURLが開かれます。

## デスクトップとWebでセッションを共有する

### OTP URLの仕組み

OTPの仕組みは、4D Secure OTPアプリケーションのアーキテクチャの中核です。ユーザーは4Dをリモートクライアントとして実行しています。Webコンソールはブラウザーで動作します。対象者の本人確認はモバイルデバイスで行われます。これらは3つの異なるプロトコルを使う3種類の別々のクライアントですが、各アクセスポイントがそのセッションから生成されたOTPによって参加を許可されているため、すべてが1つの共有セッションに参加しています。

ユーザーが**Session_Form**で**Share session**をクリックすると、次の処理が順に行われます。

1. **getOTP**がサーバー上で実行されます。Session.storageを初期化し、トークンを返します。
2. メソッドがURLを組み立てます：`http://<server>/init?$4DSID=<token>`
3. ブラウザーがこのURLにアクセスします。4Dはトークンを照合し、HTTPセッションをデスクトップセッションにリンクします。
4. 以降、このブラウザーウィンドウからのすべてのリクエストは、ユーザーのデスクトップセッションのコンテキストで実行されます。

これは、セッションを共有するURLの4Dにおける標準的なパターンです。**$4DSID**パラメーターは最初のリクエストで消費されます。その後、サーバーはブラウザーへのレスポンスでセッションcookieを設定し、以降のリクエストではトークンではなくそのcookieが使用されます。トークン自体は一度しか使えず、消費されるとすぐに無効になります。

### 2つ目のOTPによるモバイルデバイスのペアリング

ユーザーのモバイルデバイスは、Webコンテキスト内で生成される別のOTPを通じてセッションに参加します。ユーザーが/pairルートにアクセスすると、HTTPハンドラーが2つ目のトークンを生成し、それをQRコードのURLにエンコードして、ペアリング画面を表示します。

```4d
var $token : Text:=Session.createOTP(5)
var $host : Text:=$request.getHeader("host")
var $scanURL : Text:="http://"+$host+"/scan?$4DSID="+$token
var $qrURL : Text:="https://api.qrserver.com/v1/create-qr-code/?size=240x240&data="+$scanURL
```

![](fig-04)

対象者がモバイルデバイスでQRコードを読み取り、ブラウザーがエンコードされたURLにアクセスすると、4Dサーバーはそのデバイスを同じセッションに参加させます。この時点で、4Dリモートのデスクトップクライアント、ユーザーのブラウザーウィンドウ、ユーザーのモバイルブラウザーという3つのクライアントが1つのセッションを共有しています。

### Session.storage：デバイス間で状態を共有する

**Session.storage**は、セッションが存続する間保持される共有オブジェクトです。3つのクライアントはすべて同じセッションを共有しているため、**Session.storage**への書き込みは、次回の読み取り時にすべてのクライアントからすぐに参照できます。この機能を利用して、チャレンジレスポンス（challenge-response）方式の確認などが実装されています。チャレンジレスポンスの例では、最初のチャレンジが**Session.storage**を通じて共有され、その後の確認でも、選択された数字をこの共有プロパティと照合します。

## Session関数の変更点

4D 21以降、**Session.setPrivileges()**と**Session.clearPrivileges()**は、どちらも処理が成功したかどうかを示すブール値を返します。以前はこれらの関数は何も返さなかったため、開発者はアクセス権の変更が反映されたかどうかを直接確認する方法がありませんでした。ブール型の戻り値により、セキュリティ上重要な処理の流れをより厳密に制御できます。

デモプロジェクトでは、**roles.json**で設定されたアクセス権によって**uploadPhoto**クラス関数へのアクセスを制御しています。ユーザーがチャレンジに正しく回答して初めて、**/fileUpload**へのアクセス権が付与されます。

![](fig-06)

**/reply**ハンドラーは、正しい回答があった場合に**verified_user**アクセス権を付与します。

```4d
If ($correct)
    Use (Session.storage.data)
        Session.storage.data.status:="verified"
        Session.storage.data.message:="Identity confirmed. Please upload your photo."
    End use
    If (Session.setPrivileges("verified_user"))
        //continue
    end if
```

アップロードハンドラーは、ファイルを処理する前に**Session.hasPrivilege()**でアクセス権を確認します。コードの抜粋を以下に示します。

```4d
Function upload($request : 4D.IncomingMessage) : 4D.OutgoingMessage
    If (Not(Session.hasPrivilege("verified_user")))
        return This.jsonResult(New object("ok"; False; "message"; \
            "Access denied. Verify the challenge first."); 403)
    End if
    // ... proceed with upload ...
```

ユーザーが最終的な判定（承認または却下）を記録すると、**clearPrivileges()**によってセッションのアクセス権がすべて取り消され、新しいケースが開かれます。ブール型の戻り値を使えば、アプリケーションは必要に応じて、処理を続ける前に解除が成功したことを確認できます。

```4d
If ($outcome="approved") | ($outcome="rejected")
    If (Session.clearPrivileges())  // returns Boolean since 4D 21
        //proceed
    End if
End if
```

## アプリケーション全体の流れ

本書で説明したセッション機能が、4D Secure OTPの確認ワークフロー全体の中でどのように組み合わされているかを以下に示します。

![](fig-07)

> $4DSIDパラメーターは最初のリクエストで消費されます。サーバーはブラウザーへのレスポンスでセッションcookieを設定し、以降のリクエストではトークンではなくそのcookieが使用されます。トークン自体は一度しか使えず、消費されるとすぐに無効になります。**2台目のデバイスとしては、同じセッションを取得してしまわないよう、プライベートブラウズを使用してください。**

提出された各レポートには一意の参照番号（例：VR-2026-6667）が割り当てられ、保存されたセッション識別子を通じて、提出元のセッションにリンクされます。提出された証拠ファイルは、SHA-256で完全性が検証されます。画像は提出時にハッシュ化されるため、提出後に内容が変更されたり改ざんされたりすることはありません。

![](fig-08)

ユーザーが書類をアップロードすると、オペレーターはそれを確認し、ステータスを承認、却下、追加情報の要求のいずれかに設定し、ドロップダウンから理由を選択します。各ケースには一意の参照番号でアクセスできるため、提出内容を追跡し、個別に対応するのが容易です。Reportsページでは、提出されたすべての確認ケースをオペレーターが一覧で確認できます。

## ベストプラクティスとセキュリティ上の考慮事項

### OTPの有効期間

**Session.createOTP()**で生成されたトークンは一度しか使えず、システムで設定されたOTPのタイムアウト時間を過ぎると失効します。トークンは必ずユーザーに提示する直前に新しく生成し、以前に生成したトークンをキャッシュしたり再利用したりしないでください。デモアプリケーションでは、**/pair**ルートにチャレンジを再生成するボタンがあり、クリックするたびに新しいOTPを作成します。これにより、表示されるQRコードには常に有効な最新のトークンが反映されます。

### 本番環境でのHTTPS

OTPトークンはURLのクエリ文字列で送信されます。トークンが消費される前にURLを傍受した人は、誰でもそのセッションに参加できてしまいます。デモアプリケーションでは簡単のためにHTTPを使用していますが、本番環境では、通信途中でのトークンの傍受を防ぐために必ずHTTPSを使用してください。4Dプロジェクトフォルダー内の**cert.pem**と**key.pem**ファイルが、WebサーバーのTLS証明書と秘密鍵の標準的な配置場所です。

### ケース終了時のアクセス権の解除

確認ケースが最終的な状態に達したら、必ず**Session.clearPrivileges()**を呼び出してください。これを怠ると、**verified_user**アクセス権が次のケースまで有効なまま残り、対象者がチャレンジレスポンスの手順を完全に回避して、本人確認なしに証拠をアップロードできてしまいます。デモアプリケーションでは、承認または却下の判定のたびに、新しいケースを開く前にアクセス権を解除しています。

## よくある問題のトラブルシューティング

### WebハンドラーでSession.storage.dataがNullになる

OTPを生成するメソッドに「サーバー上で実行」属性が設定されていない場合、ストレージの初期化はクライアント上で実行され、HTTPハンドラーからは参照できません。メソッドにこの属性が設定されていることを確認してください。

### OTP付きのURLで「Session expired」と表示される

**/init**ルートと**/scan**ルートは、セッションデータがNullの場合に備えたチェックを行っており、データがない場合は「Session expired」というメッセージとともに403を返します。これには主に2つの原因があります。1つは、ストレージの初期化とOTPの作成がサーバー上で実行されていない場合です。この場合は「サーバー上で実行」属性を確認してください。

もう1つは、OTPの有効期限が切れた場合で、これは想定どおりの動作です。デモ用に、OTPのタイムアウトを10秒に設定しています。このタイムアウトを過ぎると、ブラウザーには403エラーが表示されます。この場合は、専用のボタンでOTPを再生成してください。

> **注**：同じセッションを取得してしまわないよう、URLは必ず別のデバイスか、プライベートブラウズで開いてください。

## まとめ

バージョン21 R3でSessionコマンドが4Dリモートクライアントに対応したことで、サーバー側への依存が減りました。セッションのメタデータの読み取りも、セッションを共有するためのトークンの生成も、クライアントから開始できるようになっています。

4D Secure OTPデモアプリケーションでは、本書で取り上げた4つの機能をすべて使用しています。デスクトップフォームでの識別情報の表示には**Session.info**を、最初のデスクトップからWebへの共有と、その後のモバイルデバイスのペアリングの両方には**Session.createOTP()**を使用しています。**Session.storage**は、デスクトップ、ブラウザー、モバイルの間でリアルタイムに共有される状態です。そして**setPrivileges()**と**clearPrivileges()**の2つの関数によってアクセス権が正しく設定され、その結果はブール型の戻り値で確認できます。
